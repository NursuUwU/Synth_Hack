**Основание:** «СИНТЕЗ_кейсы.pdf», страницы 7–9, и архив `Project_3_genomic_detecive_for_students.zip`. План обновлён после программного аудита всех десяти случаев. Подробности — в [анализе данных](Кейс_3_анализ_данных.md).

Но все поля функциональных аннотаций заполнены `NA`: их получение становится первой технической задачей. Эксперты проверяют метод и интерпретацию результатов автоматической обработки.

## 1. Что нужно успеть

Сделать работающий исследовательский прототип: описание случая и генетические варианты → обработка аннотаций → сопоставление с фенотипом и наследованием → рейтинг генов и вариантов → объяснение результата.

На защите по заданию нужны:

- Работающий прототип и демонстрация **не менее трёх клинических случаев**.
- Ранжированные списки генов и вариантов с объяснением на конкретных примерах.
- Сравнение с известным ответом там, где он есть.
- Архитектура, описание инструментов, репозиторий и инструкция запуска.
- Краткая презентация с результатами и ограничениями.

Обязательно учитывать фенотип, корректно обрабатывать отсутствие убедительного кандидата и различать сведения из баз данных, вычислительные прогнозы и предположения. Результат предназначен для исследования и обучения, не является клиническим диагнозом.

### Участник 1 — программирование и архитектура

- Читать существующие VCF/TSV и JSON без ручной пересборки. Готовый аудит использовать как отправную точку.
- Первым делом проверить получение аннотаций для небольшой партии вариантов case_01, затем обработать весь набор с локальным сохранением результатов. Получение аннотаций пока не выполнено.
- Объединять запросы по уникальным ключам вариантов с учётом GRCh38; в наборе 3 690 уникальных ключей. Сохранять источники, даты/версии аннотаций, ошибки и пропуски.
- Собрать сквозной путь на одном случае, затем подключить остальные два.
- Реализовать прозрачное ранжирование: показывать вклад доступных признаков и причины понижения позиции.
- Показывать пропущенные данные и противоречия; неизвестное значение не превращать в отрицательное доказательство.
- Сделать таблицу кандидатов и подробное объяснение для верхних позиций; подключить источник связей HPO с генами/заболеваниями.
- Автоматически оценивать позиции ожидаемых вариантов на шести development-случаях. Открытую разметку использовать для оценки отдельно от модуля ранжирования.
- Подготовить `predictions.tsv`: колонки `case_id`, `prediction`; вариант в формате `chrN:POS:REF:ALT` либо `no_causal_variant_in_vcf`.
- Подготовить запуск одной понятной командой, схему архитектуры и резервное демо.

**Готово, когда:** три случая проходят от входного файла до отчёта; другой участник может запустить проект по README.

### Участник 2 — химик: презентация и демонстрация

- Подготовить каркас презентации: задача → данные → метод → архитектура → результаты → ограничения.
- Собрать слайды из готовых материалов участников 1, 3 и 4, проверить читаемость и соответствие фактическим возможностям прототипа.
- Пройти пользовательский сценарий: открыть случай, запустить анализ, найти кандидата, прочитать объяснение. Зафиксировать непонятные места и ошибки.
- Проверить запуск по README на другом компьютере, если доступен; не брать на себя написание кода и ручную аннотацию вариантов.
- Организовать репетицию, распределить переходы между выступающими, подготовить скриншоты и резервную запись совместно с участником 1.

**Готово, когда:** есть финальные слайды, проверенный сценарий показа, список оставшихся проблем и резервные материалы. Ручная проверка тысяч строк в эту роль не входит.

### Участник 3 — химик / биолог: фенотипы и сценарии

- Использовать уже готовые HPO-профили: повторно кодировать симптомы и переписывать JSON не требуется.
- Выбрать три development-случая для основного показа, например case_01, case_03 и case_06, после проверки доступных аннотаций.
- Для каждого подготовить короткую карточку: ключевые присутствующие и исключённые признаки, опубликованный ожидаемый ответ, источник и объяснение результата системы.
- Совместно с участником 4 продумать показ конкурирующих гипотез и недостаточности данных. Открытого отрицательного контрольного случая в наборе нет; сокращённый фенотип hidden не означает отсутствия причинного варианта.
- С участником 4 проверить соответствие фенотипа кандидатным генам и заболеваниям.
- Отделять ожидаемый ответ из открытой разметки от собственного обоснования. При использовании модифицированных случаев явно указывать, какие данные изменены.
- Подготовить короткий рассказ по каждому случаю: вход → результат → объяснение → ограничение.

**Готово, когда:** у каждого сценария есть входные данные, проверяемое ожидание и понятное объяснение. Неоднозначный случай не обязан иметь единственный правильный ген.

### Участник 4 — геномика: метод и научная проверка

- Вместе с участником 1 письменно зафиксировать признаки и правила ранжирования, условия их применения и поведение при пропусках.
- Определить, как учитывать популяционную частоту, функциональное последствие, доступную клиническую интерпретацию, фенотип и совместимость с наследованием, когда эти сведения будут получены.
- Проверить механизмы болезни для демонстрационных случаев: поле наследования в разметке имеет значение `not_independently_curated`. Семейных данных и фазы для подтверждения de novo или trans в изученных файлах нет.
- Проверить, что система не приравнивает редкость к патогенности, прогноз к установленному факту, а отсутствие семейных данных — к подтверждённому наследованию.
- Проверить обработку конфликтующих интерпретаций и вариантов неопределённого значения; не выдавать их за установленную причину болезни.
- Проверить верхние позиции рейтинга и объяснения трёх демонстрационных случаев, разобрать ошибки и подготовить ответы на вопросы о достоверности. Массовую аннотацию выполняет программный конвейер.

**Готово, когда:** правила можно реализовать без догадок, а каждый основной вывод в демо опирается на конкретные данные или явно обозначенное предположение.

## 3. Объём прототипа на оставшееся время

**Первая версия:** существующие TSV/VCF и JSON → автоматическое получение аннотаций → сопоставление фенотипа → объяснимый рейтинг. В предоставленных таблицах аннотаций нет: `gene`, `consequence`, `population_AF`, `clinical_significance` заполнены `NA` во всех строках. Это основная техническая зависимость, которую проверяем первой.

Предлагаемый минимум:

- Вход: существующие файлы десяти случаев; GRCh38, 1-based, только аутосомные SNV. Генотип есть, семейных сведений в изученных JSON нет.
- Аннотации: ген, последствие, доступные частоты и клиническая интерпретация с источниками; сохранять их локально и показывать неполное покрытие. Не подменять неизвестную частоту нулём.
- Фенотип: готовые HPO-коды с учётом `excluded=true`; источник связей HPO с заболеваниями/генами подключить отдельно.
- Метод: объяснимые экспертные правила с явно указанными ограничениями. Числовой балл, если используется, обозначать как внутренний рейтинг, а не вероятность диагноза.
- Выход: рейтинг, обоснование позиций, противоречия, недостающие сведения и ответ `no_causal_variant_in_vcf`, когда метод позволяет его обосновать. Недостаток аннотаций показывать как ограничение, а не как доказательство отсутствия причинного варианта.
- Для воспроизводимости: сохранять вход, настройки правил, использованные аннотации и результат каждого демонстрационного прогона.

**После готовности обязательного минимума:** изменение симптомов или сведений о наследовании с пересчётом рейтинга — это дополнительная задача из условия.

**Откладываем до готовности основной версии:** обучение собственной модели, сложные агенты, большое число внешних интеграций и сложный интерфейс. LLM в кейсе 3 не является обязательным требованием.

- Замечание к прототипу оформляем как: **случай → фактический результат → ожидаемое поведение → обоснование → критичность**.
