# Протокол внешней проверки v1.2

**Выполнен первый цикл:** [контрольные результаты, внешний пилот и ограничения](validation_results_v1.md). Ниже сохранён исходный протокол; результаты не использовались для изменения весов, порогов или литературного реестра v1.2.

Подготовлен 12 ноября 2026 года перед получением новых результатов. Проверяемая реализация: `d1df5c05c1796482c65306d6ede7745b9a877fb5`. Версия правил: `research-v1.2-disease-context`. Исходные шесть development-случаев остаются набором разработки; четыре hidden-случая без ответов не дают измерения точности.

## До первого внешнего прогона

1. Сохранить версию кода, конфигурацию, HPO, литературный реестр и манифест аннотаций с SHA-256. Не менять веса/пороги/карточки после просмотра результатов проверочного набора. Исправление по этим результатам требует новой проверки на других случаях.
2. Заранее определить включение: GRCh38, одна точная причинная SNV, поддерживаемый генотип, клинический HPO-профиль и доступная опубликованная причинная интерпретация. Indel, CNV, несколько причинных аллелей и неподтверждённую сборку учитывать как неподдерживаемые, не как успешно решённые.
3. Фиксировать все рассмотренные случаи и причины исключения. Выбирать по техническим условиям, а не по высокому ожидаемому баллу или удобному диагнозу. Не считать несколько родственников/повторных публикаций независимыми случаями.
4. Ответы хранить отдельно от входов ранжирования. Независимый участник по возможности проверяет причинную интерпретацию по исходной публикации. Это дополнение к внешним данным; ручная рецензия текущих шести случаев сама по себе не создаёт независимый тест.

## Этап 1: контрольные сценарии

До внешних результатов выполнить на исходном наборе:

| Сценарий | Что измеряем |
|---|---|
| Удаление известного причинного варианта при сохранении остальных кандидатов и HPO | Долю случаев, где всё равно выдан статус `candidate`; какие альтернативы его получили |
| Отсутствие информативного HPO | Воздержание от итогового предсказания, сохранение причины неполноты |
| Заранее заданное удаление части признаков / добавление нерелевантных признаков | Изменения места, балла и статуса относительно исходного профиля |
| Отсутствие частоты, ClinVar либо сбой аннотации | Различение неизвестности, слабой поддержки и неполного расчёта |
| Неверный ALT, транскрипт, болезнь или составная запись ClinVar | Отсутствие неприменимой литературной/клинической поддержки; базовые unit-тесты уже существуют |

Это проверки поведения и устойчивости, **не независимая клиническая валидация**. Удаление одного опубликованного варианта не доказывает отсутствие других биологических причин. Поэтому результат такого опыта называется «контроль с удалённым известным причинным вариантом», а не клиническая специфичность.

## Этап 2: новые опубликованные случаи

Начальный практически достижимый объём — 20–30 неродственных случаев, определённый до просмотра результатов. Источник-кандидат: [Monarch Phenopacket Store](https://github.com/monarch-initiative/phenopacket-store), который содержит опубликованные фенотипы и геномные интерпретации. Закрепить конкретный релиз/хеш, не использовать плавающий `latest` в итоговом манифесте.

Исключить точные варианты, пациентов, семьи и публикации исходных учебных случаев и рабочего литературного реестра. Отдельно выделить случаи в новых генах, которых нет в шести механистических правилах. Проверить пересечение публикаций с источниками HPO/ClinVar, где это возможно; общие базы знаний не делают тест проверкой новых, ранее неизвестных генетических ассоциаций. Публичность материала и возможное знание его разработчиком также ограничивают степень ослепления.

Phenopacket с одним причинным вариантом недостаточен для оценки ранжирования сотен кандидатов. Нужен сопоставимый набор фоновых вариантов: доступный полноценный VCF либо заранее определённый синтетический фон с корректной сборкой/генотипами и проверкой наличия причинного аллеля. При использовании фона описать результат как **полусинтетический внешний тест**, а не проверку на полных клинических экзомах. Объём и состав кандидатов должны быть одинаковы для сравниваемых методов.

Для всех кандидатов получить VEP и ClinVar по одной заранее закреплённой процедуре. Текущий ClinVar-снимок на 114 вариантов исходного набора для этого недостаточен. Нельзя обновлять ClinVar только для правильных ответов или вручную добавлять функциональную карточку для каждого проверочного случая. Сохранять ошибки, пропуски, даты, параметры и хеши. Получение аннотаций и преобразование форматов допустимы до оценки; они не должны менять правила оценивания по ответам.

## Метрики

- Число рассмотренных / включённых / исключённых / неполностью обработанных случаев и причины. Процент покрытия VEP и ClinVar показывать отдельно.
- Top-1, Top-3, Top-5 и MRR для полного списка положительных случаев; отсутствие ожидаемого варианта или незавершённый расчёт не скрывать исключением из основного знаменателя. Дополнительно можно дать метрики только завершённых расчётов с явным знаменателем.
- Число статусов `candidate`, `uncertain`, `incomplete`, `no_convincing_candidate`, правильность первого места и количество ошибочных `candidate`. Неопределённый результат и отказ не объединять с уверенным ответом.
- Для контроля с удалённым вариантом отдельно показать долю `candidate`; не называть её клинической частотой ложноположительных результатов.
- Сравнить v1.1, v1.2 и фенотипический режим на одинаковых входах/источниках; указать группы равных баллов. Анализировать случаи, где комбинация улучшила или ухудшила результат относительно фенотипа.
- При небольшом объёме публиковать абсолютные числа и неопределённость оценки; не переносить процент на клиническую практику.

## Что необходимо реализовать

1. Отдельный runner контрольных сценариев и отчёт об отказе/неопределённости, не смешанный с обычной оценкой development.
2. Адаптер новых случаев с отделёнными ответами и манифестом включения/исключения.
3. Единое обновление аннотаций новых кандидатов, с локальным воспроизводимым снимком.
4. Внешний evaluation с явными знаменателями и сравнением режимов. Текущая функция `evaluate` жёстко описывает открытый development-набор и не должна выдаваться за внешний валидатор.

До защиты приоритет — контрольные сценарии, ограниченный внешний прогон и независимая рецензия наиболее спорных источников. Новые агенты, изменение LLM и расширение предметных бонусов до завершения этого прогона не нужны для проверки текущей модели.
