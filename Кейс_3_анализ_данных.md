# Кейс 3: что есть в данных и какую работу автоматизировать

**Дата:** 12 ноября 2026 года.  
**Источник:** `Project_3_genomic_detecive_for_students.zip`, включая README, objects.tsv, development_labels.tsv и все файлы десяти случаев.  
**Проверка:** программный структурный аудит всего архива. Внешняя функциональная аннотация и независимая проверка биологических интерпретаций в этот аудит не входили.

## Главный вывод для команды

**Отдельного человека на ручной анализ и очистку таблиц выделять не нужно.** Набор небольшой, единообразный и уже пригоден для программного чтения. Структурную проверку я выполнил скриптом. Загрузку, объединение, аннотацию и расчёт рейтинга следует включить в программный конвейер.

При этом данные **не готовы для содержательного ранжирования**: во всех 4 096 строках отсутствуют ген, функциональное последствие, популяционная частота и клиническая значимость. Получение аннотаций — первая техническая зависимость проекта. Мой первоначальный план опирался на предположение о готовых аннотациях; после просмотра архива этот пункт нужно изменить.

Рекомендуемое распределение: **ты — код и автоматическая обработка; химик — презентация, демонстрация и проверка пользовательского сценария; химик-биолог — объяснение случаев; специалист по геномике — метод и научная проверка.**

## 1. Состав набора

- **10 случаев:** 6 development с открытыми ответами и 4 hidden без ответов в архиве.
- На каждый случай: VCF, TSV вариантов, JSON фенотипа и JSON метаданных.
- **4 096 строк вариантов, 3 690 уникальных ключей** `chrom:pos:ref:alt` по всему набору.
- В каждом случае одна аутосома, 403–415 вариантов. Все варианты — однонуклеотидные замены, SNV.
- По README и метаданным сборка — **GRCh38**, координаты — **1-based**.
- Фенотипы уже представлены HPO-кодами и английскими названиями: **179 присутствующих и 35 явно исключённых признаков**, всего 214 записей.
- Набор составлен синтетически из фоновых вариантов GIAB HG002 и реальных клинических вариантов. По README это не геном одного пациента и не клинический бенчмарк.

## 2. Что уже проверено автоматически

В пределах перечисленных проверок структурных ошибок не обнаружено:

- Число вариантов и признаков совпадает с `objects.tsv` во всех десяти случаях.
- VCF и TSV совпадают по вариантам и генотипам, включая число повторений записей.
- Внутри каждого случая нет повторяющихся ключей вариантов.
- Идентификаторы случаев и хромосомы согласованы между файлами.
- Позиции — положительные целые числа; REF и ALT — разные одиночные буквы A/C/G/T.
- HPO-коды соответствуют формату `HP:NNNNNNN`; повторов и противоречия «присутствует и исключён» внутри одного профиля не найдено.
- Все шесть причинных вариантов из открытой разметки присутствуют в соответствующих VCF/TSV и имеют генотип `0/1`, согласующийся с указанной в разметке гетерозиготностью.

Эти проверки подтверждают согласованность файлов. Они **не проверяют** актуальность HPO-терминов по онтологии, соответствие REF референсной FASTA или правильность причинной интерпретации. В README отдельно сказано, что независимая проверка REF не проводилась.

## 3. Чего действительно не хватает

| Поле или ресурс | Фактическое состояние | Следствие для проекта |
|---|---|---|
| `gene` | `NA` в 4 096 из 4 096 строк | Сначала получить связь варианта с геном |
| `consequence` | `NA` в 4 096 из 4 096 строк | Функциональные последствия ещё не определены |
| `population_AF` | `NA` в 4 096 из 4 096 строк | Частотную фильтрацию сейчас выполнить нельзя |
| `clinical_significance` | `NA` в 4 096 из 4 096 строк | Клинической классификации в таблицах нет |
| VCF `QUAL`, `FILTER`, `INFO` | `.` во всех 4 096 записях каждого из полей | Нельзя заявлять выполненную фильтрацию по качеству секвенирования |
| Связи HPO ↔ заболевания / гены и граф HPO | В архив не включены | Одних кодов симптомов недостаточно для общего алгоритма сопоставления |
| Наследование | В открытых ответах `not_independently_curated` | Механизм нужно проверять отдельно, а не считать готовой аннотацией |
| Семья и фаза | В изученных JSON нет родословной; генотипы нефазированные | Нельзя подтвердить de novo или расположение двух вариантов в trans по этим данным |

Встречаются генотипы `1/0` наряду с `0/1`. При обработке нефазированных генотипов обе записи следует учитывать как гетерозиготные. Формат записи не должен служить признаком причинности.

`NA` — отсутствие сведений, а не частота 0 и не доброкачественная классификация. Отсутствие HPO-признака в списке также не равно его явному исключению: для этого предусмотрен `excluded=true`.

## 4. Техническая работа, которую стоит автоматизировать

1. Прочитать существующие форматы без ручного пересоздания таблиц и кодирования симптомов.
2. Объединить варианты по ключу с учётом GRCh38: для запроса аннотаций достаточно 3 690 уникальных ключей, затем результаты вернуть в каждый случай.
3. Получить функциональные и доступные частотные/клинические аннотации. README называет отсутствующие VEP/ClinVar/gnomAD; выбор способа доступа и фактическую доступность ресурсов проверить при реализации.
4. Сохранить аннотации локально с источниками, версиями или датой получения. В отчёте отдельно показывать ошибки запросов и отсутствие записи в источнике.
5. Подключить источник связей фенотипов с генами/заболеваниями и зафиксировать метод сопоставления положительных и исключённых признаков.
6. Реализовать объяснимый рейтинг и автоматическую оценку на шести development-случаях: позиция ожидаемого варианта, Top-1/Top-3/Top-5 и случаи, где аннотации не получены.
7. Сформировать итоговый `predictions.tsv` с колонками `case_id` и `prediction`. Ответ — `chrN:POS:REF:ALT` либо точная строка `no_causal_variant_in_vcf`, как требует README.

**Первая контрольная точка:** получить аннотации на небольшой партии, включающей case_01, и проверить их сопоставление с исходными ключами. До этого не стоит тратить время на сложный интерфейс.

## 5. Ограничения оценки и полезные демонстрации

- `development_labels.tsv` и `worked_example.md` содержат ответы. Их можно использовать для разработки и оценки, но модуль ранжирования не должен подставлять ответ по идентификатору случая. Результат на development следует показывать именно как результат на открытом наборе.
- Все шесть открытых ответов указывают присутствующий вариант. **Открытого отрицательного контрольного случая здесь нет.** По ним одним нельзя проверить качество отказа от ответа.
- Для проверки отказа можно подготовить отдельную, явно обозначенную модификацию development-случая с удалённым размеченным вариантом. Это проверка поведения при удалении известного ответа, а не доказательство, что все оставшиеся варианты биологически исключены.
- У case_02 и case_03 общие **406 вариантов**, но наборы не идентичны и причинный вариант каждого отсутствует в другом. Такие случаи нельзя представлять как «один VCF, разные фенотипы».
- В архиве только аутосомные SNV. Этот набор не демонстрирует работу с X-сцепленными вариантами, indel или структурными перестройками.
- Разметка ссылается на опубликованные Phenopackets и прямо предупреждает об отсутствии независимой проверки исходных публикаций. Её статус нужно сохранять в сравнении с ожидаемым ответом.
- Для hidden можно получить прогнозы, но правильность без ответов жюри пока неизвестна. Не объявлять их подтверждёнными решениями.

Для основной защиты разумно выбрать три development-случая, например case_01, case_03 и case_06, после получения аннотаций и проверки объяснений. Отдельно можно показать изменение рейтинга при изменении фенотипа и работу с сокращённым профилем hidden, явно обозначив статус результата.

## 6. Где нужен человек

**Химик:** структура и оформление презентации, понятность интерфейса, репетиция демонстрации, проверка инструкции запуска на другом компьютере, фиксация проблем пользователя. Переписывать TSV и искать тысячи вариантов вручную не требуется.

**Химик-биолог:** прочитать уже готовые профили, подготовить короткое содержательное объяснение трёх демонстрационных случаев, показать совпадения и противоречия. Проверить источники для этих объяснений совместно со специалистом по геномике.

**Специалист по геномике:** определить научно оправданные правила приоритизации, проверить механизмы наследования и верхние позиции рейтинга, разобрать ошибки и неопределённость. Это точечная экспертная работа по результатам автоматической обработки.
